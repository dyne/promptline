# DNS and resolver diagnosis

## Separate the layers

1. Confirm direct IP reachability and the application path. A routing/firewall failure is not DNS.
2. Compare NSS/application resolution with DNS queries:

```sh
getent ahosts NAME
dig NAME
dig @SERVER NAME
```

3. Inspect `/etc/nsswitch.conf`, `/etc/resolv.conf` type/target/content, DHCP or network-manager inputs, local stub/cache listeners, and `resolvectl status` only when systemd-resolved is present.
4. Check search domains, split DNS, address family, DNSSEC/time, VPN/container namespaces, and whether the application caches results.

Do not assume `/etc/resolv.conf` is a normal static file: it may be a symlink or generated by ifupdown hooks, NetworkManager, systemd-resolved, resolvconf, DHCP, a VPN, container runtime, or cloud tooling. Edit the owning configuration, not an overwritten artifact.

Use `dig +trace` only for delegation/authoritative investigation; it does not reproduce the local recursive resolver path. Compare response status, answer, authority, flags and timing. Test TCP/53 or EDNS/MTU behavior only when evidence points there.

Changing resolvers remotely can affect name-based management paths and package/service access. Preserve current values and rollback, then verify NSS, direct DNS, the application, and persistence through the owner.
